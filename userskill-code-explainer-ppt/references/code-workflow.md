# 从当前源码到可追溯的讲解

## 证据基线

- 先记录工程入口、目标平台、当前工作区状态及用户已做的未提交修改。用文件、函数和必要行号定位，不用聊天里的旧描述代替源码。

- 用户要求突出多个任务的修改时，读取指定任务的内容，以当前 diff、历史提交、备份或修改报告区分轮次。任务标题用于找到记录，不把相似标题当成同一任务。

- 保存轻量来源索引：源文件路径、函数、抽取时的行号、文件 SHA-256、旧片段的提交或快照日期。更新过的文件重新抽取相关片段，不能手改显示行号凑对应关系。

- 将来源索引、逐页内容和讲稿放在项目的中间数据文件中，供 PPT、讲稿和配音共用。最终提供源码链接或讲稿；大量内部记录留在构建目录。

推荐的中间字段（按任务裁剪，而不是固定模板）：

```json

{

  "title": "当前页主题",

  "change_round": "本轮重构 / 上轮功能 / 当前行为",

  "sources": [{"path": "src/module.c", "function": "process_frame", "line": 120, "sha256": "实际计算的摘要"}],

  "snippet": {"revision": "当前工作区", "lines": [120, 121, 125], "text": "实际抽取的代码"},

  "narration": "解释用途、调用顺序与约束的中文讲稿",

  "verification": "静态检查 / 主机测试 / 构建 / 上板等真实层级"

}

```

并行开发期间可以先编排稳定主线。正式导出前由集成负责人确认源码与最终构建事实已稳定，重新从锚点抽取片段、行号和 SHA-256，并校验 PPT 引用版本与构建快照一致。资源数字直接来自本轮最终报告，不沿用草稿中的早期结果。

用户同时授权 N 轮 bug 修复与更新演示时，为每轮保留独立问题、修改前失败用例、修复位置与修复后回归；不能把同一套测试重复跑 N 次当成 N 轮修复。无 Git 历史可使用修改前快照和逐轮记录建立依据。此要求不扩展单独制作 PPT 的代码修改权限。

更新包含界面截图的演示时，逐项绑定测试日期、代码版本和后端。旧版真实浏览器截图可以保留为历史流程证据，但需在画面与讲稿上注明；模拟 DOM、API 测试或静态渲染不能替代新增界面的真实浏览器验收。

## 讲解主线

先说明工程解决的问题和整体调用流，再沿真实入口深入关键模块。针对修改汇报，让读者看清“原先问题、修改位置、现在行为、验证证据”。架构图或处理顺序必须来自真实调用，不能用理想设计替代尚未接通的代码。

代码页重点解释接口和约束：

- 谁调用、传入什么、返回什么；队列里复制的是描述符还是数据本体。

- 谁拥有缓冲，最后一次读取发生在哪里，何时可以释放或复用。

- 正常路径与失败回收的不同处理；预览等辅助功能拥塞时是否影响主流程。

- 常量的单位、状态转换条件，以及哪些值在重构中保持不变。

中文讲解可以用中文描述长标识符；屏幕上的源码摘录保留真实代码。不要为了中文 PPT 擅自改代码字符串、许可证、厂商文件或生成标记。

## 版式与阅读

- 按内容确定页数与每页片段长度。曾用约 7–10 行的关键片段提升可读性，但不要把该范围、24 页或三段讲解写成固定要求。

- 非连续摘录保留实际行号，并让省略可辨识。修改前后都标清来源与版本。

- 中文注释需要覆盖中文字形的字体；纯代码可用等宽字体。混用两种字体时实测换行和行高，不能只按字号乘经验系数估计高亮位置。

- 原生表格用于对照、数据流、故障码和验证结果。长函数名先调整列宽和表述，不靠不断缩小字号解决拥挤。

- 讲者备注保存完整解释与来源；屏幕文字服务于听讲。可编辑原生标记框属于用户要求的讲解标注，无需生成装饰插画来替代。

- 复制旧 PPT 时尽量保留原始对象、主题、字号和图片。狭义 OOXML 媒体处理应保护未修改对象、修正关系和内容类型，并重新导入检查。

## 验证边界

| 证据 | 可以说明 | 不能据此声称 |

|---|---|---|

| 主机逻辑或合成端到端测试 | 对应输入下的软件行为及接口衔接 | 真实 RTOS 并发、硬件时序、模型准确率 |

| 编译零错误零警告 | 指定工具链和配置下构建成功 | 相机、显示器或其他外设已运行 |

| ROM/RAM 数字 | 当前构建的资源使用 | 小幅 ROM 减少证明帧率提升 |

| 占位 BSP/模型接口 | 接口框架存在 | 真实驱动或训练权重已经接入 |

资源差值从相同口径的数据计算；区分已实现的软件、未接通的生产链路和需要实板验收的工作。PPT 制作不要求重复所有固件测试，但应准确标明现有测试的日期、配置和范围。

对于 HLS/RTL 工程，验证表还应记录输入尺寸、通道/算子是否完整、执行后端和比对范围。区分 HLS 估算资源、Vivado 布线后资源、RTL 仿真周期与实板 FPS；小尺寸完整拓扑通过不等于部署尺寸完成 RTL 验证，内部时序通过也不等于达到实时吞吐。

包含预训练与个人训练的 AI 工程，应分别交代公开模型来源、原类别、是否取得原始数据，以及验证输入为真实图像还是合成/数值夹具。把安装完整性、业务验收标志、执行后端、数值误差、目标板时延与真实分类准确率分开；数值零误差和临时合成训练成功均不能证明个人识别准确率。

## 最终检查

检查每页的内容、来源、可读性及编辑能力。特别检查中英文代码换行、表格长字段、代码末行下划线/分号、页脚和高亮边框。最终渲染与源页对比：小修改可用像素差或对象差确认变动只在预期区域；这不能代替放映验证。封面概念插画不要描述为实物运行照片。若概念图含板卡、屏幕或仪器，在画面上直接标注“概念示意，非实机照片”；只在讲者备注声明不足以让观众判断图像性质。


## 项目收尾与历史讲解

用户授权清理中间版本时，按讲解主题保留各自最后交付版，而不是全项目只留日期最新的一份 PPT。先解析最终 PPTX 的关系文件、嵌入媒体和外链，确认 HTML 是否自包含；只有不被最终成果引用的草稿、渲染缓存、拆分音轨才可清理。保留讲稿、制作脚本、来源索引与小体积验证报告。旧演示标记为对应日期的代码快照，不冒充当前固件说明。

删除后的交付索引只链接实际保留文件；旧报告里的被清理路径保留为历史并说明不可直接复验。媒体完整/关系有效与 WPS 实播继续分开记录，整理文件不提升验证等级。

## 初学者讲稿与最终备注核查

批量配音前，同时检查屏幕文字与讲稿中重要术语的首次出现，给简短白话解释，并明确数字单位。新增讲者备注也要核对原文位置、指标和对照，不因正文已审就省略。仅备注修正且获审讲稿语义未变时，可保留语音，但检查最终备注及画面差异。原文图局部展示应在最终PPTX重新导入后检查裁剪；若工具往返丢失裁剪元数据，可用有出处的局部像素资产，并标明原图局部。
