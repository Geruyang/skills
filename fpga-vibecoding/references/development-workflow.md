# 项目开发与验收

本页是工程方法与验收建议，不是 FZ3B 接线手册。板卡事实见 [百度参考](baidu-fz3b.md)，机制与命令版本见 [AMD 资源](amd-resource-map.md)。按用户的当前目标选择小节，不强制把每个项目走成完整 Linux/AI 系统。

## 1. 输入、架构与工程组织

先复用现有 README、构建脚本、测试和用户决定。对缺失且影响当前动作的信息只询问必要项：功能、数据来源/去向、时钟与吞吐、数值格式、运行环境和可用硬件资料。尚未拿到摄像头、模型或板卡，不阻塞独立的软件参考及模块仿真。

用 [设计契约](../assets/design-contract.md) 的相关条目固定接口。可按现有仓库组织，或使用简洁结构：

```text
rtl/       # HDL
tb/        # 自检仿真与测试向量
hls/       # 可选：C/C++ 与 HLS 配置
scripts/   # 重建、仿真、综合、实现、报告入口
constraints/ # 时钟与板级约束分开
sw/        # PS 应用、驱动、设备树修改
docs/      # 板卡证据、接口契约、版本、验收记录
reports/   # 摘要与本次实际执行日志
```

优先提供可重建的 Tcl/配置和清晰输入，不以一个不可追溯的 GUI 工程压缩包作为唯一交付。已有工程不为适应此布局而搬迁。独立模块可并行开发，但先固定接口，并明确各代理文件所有权；无需用户采用特定治理或多代理模式。

## 2. RTL 与接口验证

- 寄存器明确位宽、符号、复位值、写入语义及完成/错误状态。输出握手与输入接受分开；不能把“发起请求”当成“请求被接受”。
- AXI4-Lite 的 AW/W/B、AR/R 各通道按握手独立处理，覆盖地址与数据不同周期到达。用自检 testbench 检查背压、连续访问、复位和非法地址。
- AXI 发送方不能等待 READY 才拉起 VALID；VALID 一旦有效，需保持有效信息直到握手完成。覆盖 READY 初始为低、延迟拉高和持续背压的场景。ALINX 第 32 章在这一点有误，见[案例勘误](alinx-case-map.md)。
- AXI4-Stream 在 `TVALID && !TREADY` 时保持有效载荷及 sideband 稳定；按接口契约处理 `TKEEP/TLAST/TUSER`。一般 packet 的 TLAST 不等同于视频帧结束，视频流常采用行/帧 sideband 约定，须对所用 IP 文档确认。
- 跨时钟域按信号语义选同步器、握手或异步 FIFO；不能逐位同步一条多位总线。复位释放与每个时钟域同步；PLL/时钟锁定与 reset sequencing 纳入验证。
- 数值模块用独立软件参考对拍，包含极值、溢出/饱和、符号扩展、舍入和非对齐边界。CNN 特别固定布局、量化零点/scale、padding 和累加宽度。

目标是捕获真实故障；不为无行为变化的文档或重命名制造镜像式测试。已有测试覆盖充分时运行相关回归即可。Verilog/SystemVerilog 评审可按需使用专用 review/lint 技能。

## 3. HLS

从可运行 C/C++ 参考与测试向量开始，先 C 仿真，再综合、C/RTL 协同仿真、IP 集成。明确 `m_axi`、`s_axilite`、`axis` 的作用，确认生成的控制协议和实际寄存器头文件。

优化依据是瓶颈与报告：流水线 II、存储端口、访存 burst、数据复用、FIFO 深度、依赖和资源。`PIPELINE` 不保证 II=1；`UNROLL` 不保证吞吐按比例增长。`DATAFLOW` 需要检查背压、死锁和通道容量。先做小数据的功能对拍，再做代表性完整尺寸的性能验证。

报告要写明输入尺寸、调用次数、目标时钟、实际 cycles/II/latency、资源和工具版本。HLS 估计频率/资源用于优化决策；交付的时序和资源以目标工程实现后报告为准。只跑小图不能推导整图 FPS。

## 4. Vivado 与 PS/PL 集成

创建项目前查询本机版本及可用 part；从精确芯片/封装/等级证据选 part。`get_parts *zu3eg*` 是查询线索，不是“返回任意一项即可”。原厂 PS preset 需要与实物 DDR/MIO/时钟和板修订匹配。

在已经核验的 PS 基线上，先打通最小控制通路，再打通数据通路：

1. PS 到 AXI-Lite 控制寄存器：核验 master/slave 方向、地址分配、时钟、复位、中断。
2. PL 访问 PS DDR：按 MPSoC 的 HP/HPC 等端口和所需事务属性设计，不能抄 Zynq-7000 的 GP/HP 端口名称。检查各时钟域和 AXI clock converter/reset 关系。
3. 固化地址映射、数据位宽、burst、地址宽度和软件 ABI；以导出的硬件平台和生成头文件核对软件。
4. BD 校验、综合、实现、DRC、CDC、时序报告通过对应要求后导出 XSA/bitstream；后续软件使用同一代硬件描述。

完整板级约束应有来自实板资料的 pin、Bank/VCCO、标准、时钟与外部 I/O 时序。OOC 时钟约束单独保存。不能通过降低 UCIO/NSTD 严重程度或普遍加 false path 获得“可用 bitstream”。CDC 约束、异步时钟组和 false/multicycle path 必须有结构和时序意图依据。

检查 setup/hold、unconstrained paths、clock interaction、CDC、DRC 和利用率；对警告给具体处置，不只看 WNS 为正。保持关键报告及输入源文件哈希，区分内部路径时序和板外接口时序。

## 5. AXI DMA 与内存

先做小缓冲区 loopback，再加入算法。区分 MM2S 与 S2MM，明确 simple/SG 模式、DMA 长度字段、DRE、对齐、地址宽度、TLAST 与错误/中断状态。长度上限由实际配置和当前 PG021 确认，不能照抄教程常数。

裸机非一致性通路需正确维护 cache，并保证 CPU/DMA 缓冲区所有权和顺序；cache 操作与边界按当前 BSP API 核验。Linux 驱动使用目标内核的 DMA API 和必要的内存屏障，不把用户虚拟地址直接交给 DMA，也不把裸机 cache API 移植到 Linux。区分 CPU 虚拟、CPU 物理与 DMA/bus 地址；考虑 DMA mask、SMMU/IOMMU 和设备树描述。

使用 HPC 端口本身不自动构成一致性；必须核对 AXI cache/shareability 属性、PS 配置、软件分配与映射方式。`dma-coherent` 不能把非一致性硬件“变为”一致性。UIO/`/dev/mem` 只能在已理解风险与映射的诊断场景中使用，不能替代完整 DMA buffer 管理。

验收至少观察数据完整性、短包/长包与非对齐边界、超时、重复启动、错误恢复、中断处理、缓存交接、持续传输速率；问题定位先读状态寄存器/驱动日志，再用 ILA 对照握手与 TLAST。

## 6. 软件、BSP 与启动链

保留原厂镜像作为可回退基线。先记录板上系统/内核、rootfs、驱动、推理库、固件版本及来源，再决定只改用户态应用还是重建平台。普通 Linux 应用不必先重建 PetaLinux。

需要自建平台时，按版本核对 Vivado XSA、Vitis BSP/编译器、PetaLinux/Yocto、Linux、U-Boot、设备树和 IP 驱动。经典 SDK/XSCT 与 Vitis Unified 的操作与 API 不是通用脚本；参考同一版本官方文档。Windows Vivado 与 Linux 构建环境分别记录；不要无依据承诺某版 PetaLinux 在 WSL/容器受官方支持。

ZynqMP 启动通常涉及 BootROM、FSBL、PMUFW，以及所选软件栈中的 ATF、U-Boot、内核/DT/rootfs 和可选 PL 配置。具体分区、加载地址、启动核与顺序按目标 release 的 UG1137/UG1283 和厂商 BIF/镜像确认；不提供猜测地址的通用 BOOT.BIN。

修改 Linux 外设时同步核对 `compatible`、地址、中断、时钟、reset、DMA 和绑定文档；设备树从匹配 XSA/平台派生。内核模块必须针对运行内核及配置交叉编译，主机编译通过不等于板上驱动可用。

写 SD/eMMC/QSPI 或换 bitstream 前明确实际设备、备份、回退镜像和恢复接法。创建技能不授权操作硬件。真实开发任务中，用户已明确授权的操作无需重复询问；缺少决定性目标或不可逆操作授权时才补齐。

## 7. 摄像头、视频与 AI

先核验摄像头是 USB UVC、网络流还是直连 MIPI/并行接口；产品有连接器不证明系统已支持该传感器、lane 数、格式或驱动。固定分辨率、帧率、stride、像素布局、字节序、色彩空间与时间戳。

模型先检查算子/shape/布局、预处理、后处理、量化和版本支持，再尝试上板。原厂路径使用与软核配套的模型工具和 SDK；自研路径需要自己的算子实现、驱动和数据流。不能假定 Vitis AI DPU、百度原厂引擎和自写 CNN 具有相同模型 ABI。

资源预算看 LUT/FF/BRAM/DSP、权重与特征图容量、带宽和访问次数；不要把 154K logic cells 当作 154K LUT。估算时明确一次 MAC 计 1 还是 2 operations、INT8/FP16 等精度和工作负载，不以标称 TOPS 推导任意模型 FPS。

性能分段测采集、预处理、传输、内核、后处理和显示/网络，并测端到端延迟、持续 FPS、丢帧、队列深度和内存增长。用代表数据集测精度；合成权重只证明路径运行。资源不够时根据测量选择降分辨率、量化、数据复用、分块或 PS/PL 划分。

## 8. 调试与完成标准

逐层排查：供电/指示与正确启动介质 → 串口启动日志 → 软件版本/驱动 → AXI 地址与状态 → ILA 握手与 reset/clock → 算法数据。先定位首个异常层，不用重刷整个系统替代诊断。

| 等级 | 可以报告的结论 | 不能据此报告 |
|---|---|---|
| 软件参考/RTL 仿真 | 所列向量、协议场景通过 | 板上实时运行 |
| HLS 综合/协同仿真 | 给定测试规模功能和周期 | 实际 DDR 带宽、整图功耗 |
| 器件级 OOC 实现 | 指定 part/时钟内部时序与资源 | FZ3B 引脚、DDR、启动有效 |
| 板级工程实现 | 核验配置下的 DRC/时序/产物 | 已连接实物并工作 |
| 实板闭环 | 该板、该镜像、该负载的实测结果 | 其他 PCB/版本自动通过 |

验收记录给出：输入/源码/模型/镜像标识、命令、工具版本、实际时间与日志、通过范围、已知失败和下一步。只列本次执行或有可追溯历史证据的测试，不把“计划验证”写为 PASS。
