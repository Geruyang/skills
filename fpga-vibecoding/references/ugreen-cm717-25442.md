## FZ3B 连接路线与本用户基线

摄像头 USB-A 插头 → FZ3B 的 USB Host 口 → Linux UVC/V4L2 → 图像解码/预处理 → 应用或原厂 AI 推理。摄像头是外设，板卡保持 Host；不需要恢复之前的 USB Device/g_ether 方案，也不能用摄像头代替板卡与 PC 的 USB 文件传输连接。

[百度 EdgeBoard 产品介绍](https://ai.baidu.com/ai-doc/HWCE/Qkda68drw)中 FZ3A/B 对比表列出 USB Camera (UVC)；这是板卡产品能力声明，不是对 CM717 的兼容性认证。优先使用原厂系统已有 UVC 驱动，不为接普通 USB 摄像头重建 PL、替换 bitstream 或升级整套 BSP。

## 首次接入的最小验证

先核对实物标签和插入前后设备差异，再确定设备节点；不能固定 `/dev/video0`，也不能把所有 video 节点当成独立摄像头。设备能力通过 [V4L2 ENUM_FMT](https://docs.kernel.org/userspace-api/media/v4l/vidioc-enum-fmt.html) 等枚举确认；设置后必须读回，因为 [S_FMT 可调整请求参数](https://docs.kernel.org/userspace-api/media/v4l/vidioc-g-fmt.html)。

以下为上板流程示例，实测执行情况见末节。先检查工具存在及其本机帮助，不为取得工具自动升级原厂系统。

```sh
uname -a
lsusb
lsusb -t
dmesg | tail -100
command -v v4l2-ctl
v4l2-ctl --help
v4l2-ctl --list-devices
ls -l /dev/v4l/by-id /dev/v4l/by-path
```

从实际枚举中选择 Video Capture 节点，用它替换下面的 `/dev/videoN`。优先记录稳定的 by-id/by-path（若存在），以及 sysfs 路径、驱动、VID:PID、产品名、序列号/固件版本（若提供）。

```sh
camera_dev=/dev/videoN
v4l2-ctl -d "$camera_dev" --all
v4l2-ctl -d "$camera_dev" --list-formats-ext
v4l2-ctl -d "$camera_dev" --list-ctrls-menus
```

1. 确认 USB Video 接口绑定 `uvcvideo` 并支持采集。驱动可能内建，`lsmod` 没显示不等于缺驱动；结合 sysfs、内核配置及日志。音频接口按需单独验证。
2. 从列出的格式、尺寸、帧间隔组合选一个较低负载基线，采集一张或少量图像并检查解码内容，再提高到业务所需模式。720p/1080p/2K 只是候选级别，未枚举到的组合不强设。
3. 同时具备 MJPG 和 YUYV 时，比较链路带宽与 ARM 解码成本。不要预设本机支持 H.264 或任意硬件解码，也不要把 2K30 宣传值当成每种像素格式的能力。
4. 设置格式和帧率后读取 `--get-fmt-video`、`--get-parm`；应用打开设备可能再次改格式，因此最终以采集进程实际协商结果为准。OpenCV 的 `set()` 成功不独立证明实际尺寸/FPS。
5. 做有时限的连续采集，记录协商模式、帧数、实际耗时/FPS、错误/丢帧（若可测）、CPU 与内存、图像质量；之后才接模型推理。稳定性测试时长由业务目标决定。

在已选好并读回模式后，可用下面命令进行至多 30 秒、最多 300 帧的传输检查（不保存图像）。`timeout` 返回 124 时记为超时，不写成测试通过。帧成功接收仍需要另做图像内容检查。

```sh
timeout 30s v4l2-ctl -d "$camera_dev" \
  --stream-mmap=4 --stream-count=300 --stream-to=/dev/null
```

命令依据：[v4l-utils 上游 v4l2-ctl 手册](https://raw.githubusercontent.com/gjasny/v4l-utils/master/utils/v4l2-ctl/v4l2-ctl.1.in)。该链接为当前 master；旧系统选项以板上 `--help-all` 为准，不假定其具备新版全部功能。

## 带宽、控制与算法集成

带宽估算属于工程计算，不是本型号实测：若使用 16 bit/pixel 的 YUYV，`宽×高×2×FPS` 为图像净数据率；1920×1080×30 约 124.4 MB/s，若 2K 模式实际为 2560×1440×30 则约 221.2 MB/s，均超过 USB2 的 60 MB/s 理论总线速率，且尚未计算协议开销。若摄像头枚举在 480M，高分辨率高帧率通常需要压缩或降低模式；压缩支持必须实测枚举，不能由该计算反推出一定支持 MJPG。

自动曝光可能降低暗处实际帧率，自动对焦可能导致画面短时变化。先读取可用控件、范围、菜单和当前值，再按任务需要调整并记录；不写死 `exposure_auto` 枚举值，不推定 `focus_auto` 一定存在。固定工作距离的标定/检测可在实证支持后评估锁定焦距与曝光。[Linux UVC 文档](https://docs.kernel.org/userspace-api/media/drivers/uvcvideo.html)描述标准/扩展控制机制，不代表该摄像头实现了所有控件，更不保证旧内核具备新文档全部功能。

接入原厂 AI 应用时保留单独的视频采集基线，明确 MJPEG 解码、YUYV/BGR/RGB 转换、resize/crop/letterbox、归一化与模型输入布局。USB 图像首先到 PS/Linux；要接自研 PL，另外设计 DDR/AXI/DMA 数据路径，不能把 USB 摄像头理解为直接给 PL 输出 MIPI 或像素总线。端到端 FPS 应包含采集、解码、预处理、推理与后处理，不拿摄像头 30fps 代替整机成绩。

后续实测回写仅升级已有证据的字段：实物型号/批次、VID:PID、内核/工具版本、USB 路径与速度、格式/帧率完整枚举、实际采用模式、控件、图像样本、连续测试结果和日志位置。

## 同日帧率优化追补（16:45—16:59）
